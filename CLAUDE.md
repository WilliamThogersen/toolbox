# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`toolbox` is a Rust CLI (installed as `toolbox` with a `tb` symlink) whose commands are defined at runtime, not compiled in. Each command is a folder `$TOOLBOX_HOME/commands/<name>/` (default `~/.toolbox`) holding `command.json` (name, args, permissions) and `run.lua` (Lua 5.5, sandboxed). It also has a vault: API keys that commands can use in HTTP headers without the script (or the AI writing it) ever seeing the value.

## Commands

```bash
cargo build
cargo test                              # unit tests + end-to-end tests
cargo test --test cli                   # end-to-end tests only (tests/cli.rs)
cargo test vault::inject                # one module's unit tests
cargo test --test cli secret_requests   # one end-to-end test by name filter
cargo clippy --all-targets              # keep at 0 warnings (lint set in Cargo.toml [lints] + clippy.toml)
cargo deny --target aarch64-apple-darwin check   # advisories, licenses, sources (deny.toml); CI runs every shipped target
```

The Rust version is pinned in `rust-toolchain.toml` (rustup installs it on first build, CI included).

Run the dev binary against a throwaway home and a plain-text test vault (never put real keys in it):

```bash
TOOLBOX_HOME=/tmp/tbhome TOOLBOX_INSECURE_TEST_VAULT=/tmp/tbhome/vault.json target/debug/toolbox self new hello
```

Without `TOOLBOX_INSECURE_TEST_VAULT`, vault commands hit the real macOS Keychain item (service `toolbox`, account `vault`). Other systems have no vault (`vault/platform/other.rs` refuses every load and save): the Linux Secret Service hands items to any process of the user, so it can't keep keys from agents. `keyring` is a macOS-only dependency; don't add a Linux store without a per-program access check.

## Architecture

**Layout**: `src/` holds only `main.rs` and folders. `cli/` is the top-level app (`mod.rs`), panic-free arg lookups (`matches.rs`), data paths (`paths.rs`), terminal-safe text (`screen.rs`) and the new-version notice (`notice.rs`). `builtin/` has one file per `tb self` command. `command/` is what a command is (`manifest.rs`) and how they load (`registry.rs`). Then `install/`, `mcp/`, `runtime/`, `sys/`, `vault/`. A new file goes in the folder of its domain, never in the `src/` root.

**No comments in `src/`** except `// SAFETY:` on `unsafe` blocks. Names say what code does; the why lives here and in `docs/`. When a change rests on a non-obvious reason, add it to "Why the code is the way it is" below, not as a comment. Tests in `tests/` may keep comments.

**Startup flow** (`main.rs` -> `cli/mod.rs`): load every command folder (`command/registry.rs`), build the clap app dynamically with one subcommand per valid manifest, then dispatch. Broken commands never break startup: they are collected as `Problem`s and surfaced by `tb self check` and `tb self describe`.

**Top level vs `self`**: plain `tb` lists only the user's commands (custom help template in `cli/mod.rs`, clap's help subcommand and `-h`/`-V` hidden). All built-ins (`new`, `check`, `describe`, `guide`, `install`, `update`, `uninstall`, `vault`) live under the hidden `self` namespace in `src/builtin/` (`app.rs` defines them, `mod.rs` and `vault.rs` run them; read args through `cli/matches.rs`, never clap's panicking `get_one`/`get_flag`). New built-in features go under `tb self`, never the top level. Reserved top-level names are in `manifest::RESERVED_NAMES`.

**Output contract**: stdout carries only the JSON result. Lua `print`/`log` go to stderr. Errors are `{"error": ...}` on stderr with exit 1 (plain text when stderr is a TTY). A closed stdout pipe is not an error (`cli::ignore_closed_pipe`). After every run, `cli::notice::notify` may print a new-version notice to stderr: only when stderr is a TTY and `TOOLBOX_NO_UPDATE_CHECK` is unset, asking the GitHub releases API at most once a day (cached in `$TOOLBOX_HOME/update-check.json`), so agents never see it.

**MCP** (`src/mcp/`): `tb self mcp` serves user commands as MCP tools over stdio (newline-delimited JSON-RPC 2.0). Each `tools/call` runs `tb <command> --<arg>=<value>` as a child process with stdin from `/dev/null`, so a script can't read the protocol stream and keys go through exactly the CLI's path. The child calls `setsid`: MCP clients start servers on their own terminal, and a child holding it could open a vault prompt there (`exec` of `tb self vault allow`). `tests/mcp.rs` starts the server with a real controlling pty to prove calls can't reach it. Calls run on their own threads; every write holds the stdout lock for a whole line. `running.rs` tracks each call's process group so `notifications/cancelled` and stdin EOF stop it: SIGTERM first (so `tb` can end the `exec` programs it put in groups of their own), then SIGKILL after `GRACE` (2 s) if the call is still running. Built-ins are never tools. After `notifications/initialized`, a watcher polls the commands folder and sends `notifications/tools/list_changed` when a manifest changes. End-to-end tests are in `tests/mcp.rs`.

**Runtime** (`src/runtime/`): every run gets a fresh Lua state. `sandbox.rs` removes `io`, `os`, `load`, `dofile`, `loadfile`, `require`, `string.dump`. `api.rs` installs `json`, `log`/`print`, `env`, `vault`, `stdin`; `exec.rs` installs `exec`; `fs.rs` installs `fs` (paths checked after resolving symlinks against `permissions.read`/`write`); `http.rs` installs `http`. `time.rs` and `encoding.rs` (`base64`, `url`, `hash`) are pure and need no permission. `limits.rs` caps each run at 60 s of CPU time (a global instruction hook reading the thread's CPU clock, so coroutines are covered) and 512 MB of Lua memory, unless the manifest's `limits` asks for more; a script that catches the CPU error with `pcall` gets the process ended at the next check. Everything that reaches outside the process is gated by a field in `manifest::Permissions`. Helpers that could take a vault placeholder (`base64`, `url.encode`, `hash`) refuse it, since only http header values get substituted. `run.lua` must return a function. Its return value is converted to JSON. Use `runtime::ser_options()` whenever converting JSON into Lua so JSON `null` becomes `nil`.

**Installing from git** (`src/install/`): `tb self install <url>` fetches one commit with the user's own `git` (`git.rs`: `init` + `fetch --depth 1`, so `--ref` takes a branch, tag or SHA). `repo.rs` finds commands at the repo root or one per top-level folder, rejects symlinks and checks manifests plus Lua syntax. `repo::select` picks the named commands (each must exist and be valid, or nothing installs) or, without names, every valid one while reporting the broken as `skipped`. Only `command.json` and `run.lua` are copied, plus `.source.json` (url, ref, commit), through a staging folder in `$TOOLBOX_HOME` so the final move is a rename. `update.rs` compares the manifest's semver `version` when both sides have one, else the commit, and asks before every update (new code needs a yes, even with the same permissions). `confirm::warnings` labels risky permissions (`exec`, `http *`, `env`, `vault`) in both prompts. Asking goes through the `Confirm` trait: `Prompt` needs a TTY and otherwise fails with the permission summary, `Yes` is `--yes`. `uninstall` only removes folders that have `.source.json`. `market.rs` keeps saved marketplaces in `$TOOLBOX_HOME/markets.json`, resolves `acme/stars` and `acme stars` to a repo plus names (anything else is a URL or path), and `search` fetches each saved marketplace fresh.

**Claude Code setup** (`builtin/init.rs`): `tb self init` writes `docs/agent-instructions.md` (compiled in) to `TOOLBOX.md` in `$CLAUDE_CONFIG_DIR` or `~/.claude` and appends an `@TOOLBOX.md` line to `CLAUDE.md` there, never twice. It only overwrites or deletes a `TOOLBOX.md` starting with its marker comment. `--remove` undoes both. Keep that file short: Claude loads it into every session.

**Code rules** (`docs/code-rules.md`): NASA's "Power of 10" in Rust, mostly enforced by the `[lints]` table in `Cargo.toml` and `clippy.toml`. In short: no recursion (walk trees with a worklist); every `loop`/`while` has its bound in its condition, or is one of the loops listed in `docs/code-rules.md` with its bound; no `unwrap`/`expect`/`panic!`/`unreachable!`/fallible indexing outside tests, return errors instead; functions at most 60 code lines; every buffer filled from outside the process is capped (`runtime::read_capped`, 20 MB; MCP messages 4 MB); `let _ =` marks a deliberately dropped `Result` (the reasons are listed below). `unsafe` lives only in `src/sys/` (each block one operation with a `// SAFETY:` comment), and `#[cfg(target_os)]` only in `src/vault/platform/mod.rs` and `src/sys/mod.rs`. Exceptions use `#[expect(lint, reason = "...")]` in `src/` (tests may `#[allow]` with a reason).

**Adding a Lua capability** touches three places: the `Permissions` struct (manifests use `deny_unknown_fields`, so new fields must be declared), the binding in `src/runtime/`, and `docs/writing-commands.md`. That file is compiled in and printed by `tb self guide`: it is the API reference AI agents read before writing commands, so keep it in sync.

**Docs** live in `docs/`: one page per `tb self` command in `docs/commands/<name>.md`, linked from `docs/README.md`, plus topic pages (`sharing.md`, `security.md`, `ai-agents.md`, `development.md`). The root README is a short front page that links there. `builtin::tests::every_builtin_is_documented` fails when a built-in, subcommand or flag has no page, so a new built-in or flag needs its docs in the same change.

## Vault invariants (security-critical)

The design goal: an agent with full shell access that writes `run.lua` and `command.json` must not be able to read a stored key.

- Secret values never enter the Lua state. `vault("name")` only returns the placeholder `{{vault:name}}` (`{{vault:name|base64}}` with `"base64"`, for Basic auth). Substitution happens only in `runtime/http.rs` via `vault::inject::Injector`, in header values and in `query = {...}` values. Placeholders in the URL string, body, header names or query names are errors.
- `Injector::authorize` requires all of: the secret is listed in the manifest's `permissions.vault`, it exists, the URL is https (plain http only for loopback), a rule in the secret's human-set `hosts` allows the host and port (`vault::hosts::allows`), a query placement uses a parameter in its `query_params`, and the command is approved (`vault::approval::check`). Approval is checked last so agents fix their own mistakes before asking the human.
- Approval (`tb self vault allow`) stores the SHA-256 of `command.json` + `run.lua` in the secret's `commands` map. `runtime::run` reads `run.lua` once and both fingerprints and executes that same text, and `CommandDef::manifest_source` is the text the manifest was parsed from. Any edit needs a new approval. The allow prompt (`approval::review`) shows a short screen with every script line that reaches outside the sandbox (`http`, `exec`, `fs`, `env`, `stdin`, `vault`, `_G`, `_ENV`, `rawget`, URLs), and `v` pages the whole numbered script through `/usr/bin/less` on `/dev/tty`. Both go through `screen::printable`, which escapes control and bidi characters; the install and update prompts use it too, plus `screen::one_line` for manifest values.
- Host rules for this computer must be one loopback address with a port (`127.0.0.1:8080`, `[::1]:8080`): an agent can listen on any free local port, and `localhost` resolves to both address families, so it could take the one the real server doesn't use. `localhost`, `*.localhost` and `0.0.0.0` rules are refused, and old port-less local rules match nothing (`vault::hosts`). Script-controlled text (like a query parameter name) never goes into the "ask the user to run" hints unless it passes the same validation as the CLI.
- Storage format 3 (`store::encode`/`decode`) keeps keys under `keys`, not `secrets`, so toolbox 0.3.0 (which the Keychain may still trust and which ignores approvals) sees an empty vault, and 0.4.0 to 0.6.0 (which only open format 2 and never ask for Touch ID) refuse it. Formats 2 and 3 load; saves write 3. Format 1 still loads, without approvals. `Stored` and `SecretEntry` use `deny_unknown_fields`, so a vault from a newer toolbox fails closed instead of having its rules ignored. Bump `FORMAT` when adding a rule older binaries must not skip.
- Requests carrying a secret use the `secret_safe` agent: no redirects, no env proxy. Responses and error strings go through `inject::Redactor` before Lua sees them. `Redactor::redact` also undoes up to 3 layers of JSON escapes in any text (`vault::unescape`) and replaces keys found there where they sit, since escapes like `\u0074` or `\/` hide a key from the exact match and `json.decode` or a script's own unescaping would undo them. JSON bodies are scrubbed again after parsing as a backstop (`redact_response`).
- The whole vault is a single Keychain item, so host bindings can't be edited without the Keychain's permission prompt. Storage goes through the `VaultStore` trait: `KeychainStore` (`vault/platform/macos.rs`), `FileStore` (tests only), `MemoryStore` (unit tests).
- Every vault write (`add`, `allow`, `revoke`, `rm`) reads from `/dev/tty` through the `Terminal` trait, so an agent's shell (no controlling TTY) cannot add, change, approve or delete anything. A pseudo-terminal (`script`, `expect`) gets past that check, so `KeychainStore::save` also asks for Touch ID or the login password through LocalAuthentication (`sys::macos::confirm_presence`), with a sentence naming the change (the `change` argument of `VaultStore::save`). It lives in the store so no write path can skip it; `FileStore` and `MemoryStore` don't ask. The end-to-end tests detach with `setsid` to reproduce this, and write approvals straight into the test vault file (`Toolbox::allow`, which mirrors the fingerprint format).
- `vault::log` records every add, allow, decline, revoke, remove, use and refusal: key names, command, method, host and path (never the query string or a value), plus the parent process chain and whether a terminal was attached. It goes to `$TOOLBOX_HOME/vault-log.jsonl` (0600, rotated at 5 MB) and, unless the test vault is in use, to the system log via `syslog(3)`, which an agent can't edit. Logging never blocks a command.
- `tb self vault request` is the one vault command that needs no terminal: it writes only `$TOOLBOX_HOME/vault-requests.json` (`vault::requests`), never the vault. Everything in that file is agent-written: `requests::load` checks each entry again and drops broken, repeated and over-limit ones, a request names at most 5 hosts, and its required `why` and optional `note` must pass `screen::printable` unchanged. `vault::setup` asks for each requested key (Enter keeps the requested hosts), reviews every command waiting for a key, and saves the whole batch with one `store.save`, so one Touch ID covers it and nothing is saved before the end. Its Touch ID sentence names commands getting a key that was already stored first. Agent hints point at `request` for a missing key and `setup <command>` for a command not allowed or changed.
- Never add a command or API that returns secret values. `SecretValue`'s `Debug` is redacted, and `expose()` belongs only in the injection path.
- The end-to-end tests in `tests/cli.rs` (redaction, host and port binding, command approval, proxy bypass, exfiltration attempts, TTY requirement) are the security spec. They run the real binary against local TCP echo/proxy servers on loopback. Keep them passing when touching `src/vault/` or `src/runtime/http.rs`.

Known limits (documented in README): a rebuilt binary can read the vault after the user approves the Keychain prompt, and redaction only catches exact (raw, base64, URL-encoded) copies of a key.

## Why the code is the way it is

Reasons that used to be comments. Read the relevant bullets before changing that code.

- **exec** (`runtime/exec.rs`): no shell. The child's env is cleared; only `BASE_ENV`, `LC_*` and `permissions.env` pass, so tokens in an agent's shell stay out. `opts.env` may not set `CODE_ENV` (`PATH`, `BASH_ENV`, `ENV`, `SHELLOPTS`, `BASHOPTS`, `PS4`) or `LD_*`/`DYLD_*`, and names with `=` or NUL are refused (`PATH=/tmp/evil:` = `x` reaches the child as `PATH=...`). The program is found with toolbox's own `PATH` before `cwd` applies, so `cwd`/`env` can't swap it. With a timeout the child leads its own process group, so the kill also stops what it started. Both pipes drain on their own threads while it runs; past 20 MB the rest is read into a sink so the child never blocks on a full pipe.
- **fs** (`runtime/fs.rs`): write roots are also read roots; a root that can't be resolved allows nothing. A path outside the roots gets the same denial whether or not it exists, so errors can't reveal what exists (`written_inside` ignores `..` for that reason). `real()` resolves symlinks in the existing part; the missing tail can't hold `..`. `read` checks the file type before opening, since opening a FIFO blocks forever. `remove` removes a symlink, never its target.
- **sandbox/limits**: precompiled Lua chunks are refused (Lua doesn't verify bytecode). The CPU hook is global so coroutines inherit it; a C function like `string.rep` counts as one instruction. The CPU limit fails closed: `sys::thread_cpu_time` returns `None` when the clock can't be read, which fails the run at start and counts as over the limit later.
- **exec timeout**: without `timeout`, `exec` gives up after `DEFAULT_TIMEOUT` (10 min), since waiting uses no CPU time and the CPU limit can't end it. Only an explicit `timeout` puts the program in its own process group (killing the group stops what it started). The default keeps it in `tb`'s group, so Ctrl-C and an MCP cancel still reach it; on timeout it is killed directly. A program in its own group is out of reach of signals sent to `tb`'s group, so `main` installs `sys::stop_children_on_termination`: on SIGINT, SIGTERM or SIGHUP the handler SIGKILLs the group `exec` registered (`sys::WatchedGroup`, the one static in the crate, since a signal handler can reach nothing else), SIGKILLs `tb`'s own group when `tb` leads its session (MCP calls, never a shell job, where that group holds the user's pipeline), then re-raises the signal. Everything in the handler is async-signal-safe: atomics, `kill`, `getsid`, `getpid`, `raise`. `tests/cli.rs` and `tests/mcp.rs` prove Ctrl-C, SIGTERM and an MCP cancel each end such a program.
- **panics and overflow**: release builds keep `overflow-checks`, so arithmetic overflow stops the run instead of wrapping to a wrong value. `main` installs a panic hook that reports any panic through `cli::report_error`, so even then stderr is `{"error": ...}`.
- **http** (`runtime/http.rs`): the vault loads lazily, so commands without secrets never touch the Keychain. ureq follows no redirects (`max_redirects(0)`); `follow` does, checking each hop's host against `permissions.http`, dropping `authorization`, `cookie`, `content-length`, and the timeout covers the whole chain. Requests with a secret never follow redirects. Form/query placeholders are checked before URL-encoding, since escaped ones would no longer be recognised. The key log's request has no query string, which may hold the key.
- **redaction** (`vault/inject.rs`, `vault/unescape.rs`): needles go longest first, so a secret containing another is replaced whole. A `user:password` secret also redacts the password when it is at least `MIN_SECRET_LEN` (8) long; shorter values would mangle normal text. JSON escapes are undone up to `ESCAPE_LAYERS` (3) deep; hits map back to where they sit in the original text.
- **approval** (`vault/approval.rs`): the fingerprint prefixes each file with its length, so bytes can't shift between `command.json` and `run.lua`. The review shows at most `MAX_SHOWN` (25) reaching lines. The pager is `/usr/bin/less`, never the first `less` in `PATH`.
- **Touch ID sentence** (`commands::add_change`, `setup::change`): moving an existing key to new hosts, and commands getting a key that was already stored, come first and read differently from adding a key. With a faked terminal that sentence is all the person reads.
- **requests** (`vault/requests.rs`): agent-written, so nothing is trusted. At most `MAX_REQUESTS` (20, more buries the human in prompts), `MAX_HOSTS` (5, a long list could hide a bad host), `MAX_TEXT_LEN` (200) for `why`/`note`; runs of spaces collapse so text can't fake extra lines. Entries parse one by one so one bad entry doesn't block the rest. Saves go through a temp file + rename.
- **setup** (`vault/setup.rs`): nothing is saved until the end, in one `store.save`. In a sweep, a command whose script can't be read is skipped, not fatal, so pasted keys aren't lost. `forget_fulfilled` reads the file again, so a request filed meanwhile stays. A missing key in `grant` is a bug and stops before saving.
- **key log** (`vault/log.rs`): recording never fails a command, since a file an agent made unwritable must not become a way to break commands; the system log is the copy that counts. One write per entry, so parallel runs don't interleave. `by` holds program paths, not names (Claude Code's process is named after its version).
- **Keychain** (`vault/platform/macos.rs`): keyring's `v1` store has no fallback; keep it that way, since a store that forgets keys or uses a plain file would break the vault. `store_status()` is checked first because `Entry::new` only says "no store".
- **hosts** (`vault/hosts.rs`): `127.1` normalizes to `127.0.0.1`; the only IPv6 accepted is `[::1]`. Query parameter names keep their case (servers differ).
- **install** (`install/git.rs`): git runs with `-c protocol.ext.allow=never`, since `ext::` URLs run shell commands. `marketplace add` fetches once so a typo fails right away.
- **MCP**: tool args are always `--name=value`, so a value starting with `-` stays a value. Protocol `2025-03-26` is left out: it requires JSON-RPC batches. The watcher takes its first fingerprint before reading the next message, so a command added right after the handshake isn't missed. A session leader's process group id is its pid (`running.started`).
- **sys**: `kill_process_group` refuses ids 0 and 1, which would mean our own group or every process.
- **terminal text** (`cli/screen.rs`): `printable` escapes ANSI codes, carriage returns, bidi marks and overrides (Trojan Source) and zero-width spaces. `one_line` keeps manifest fields to one line, since a newline could print a fake `permissions:` line.
- **Deliberate `let _ =`**: an exec pipe read error (what arrived is still returned), sends on a channel whose receiver may be gone (exec after a timeout, MCP replies after the client left), killing and reaping a timed-out child, writing the update-check cache (failure only means asking again), writing to `less` (quitting early closes the pipe), joining MCP call threads at shutdown.

## Repo

Pushes go to the `main` branch of `github.com/WilliamThogersen/toolbox` through a repo-local credential helper (`git config --local -l`). Don't change the global `gh` account to push.

CI: `.github/workflows/ci.yml` runs `cargo test` and `cargo clippy --all-targets -- -D warnings` on `macos-latest` and `ubuntu-latest` for every push to `main` and every pull request. `.github/workflows/deny.yml` runs `cargo deny check` (`deny.toml`) once per shipped target on the same triggers and daily, since new advisories appear without code changes. Per target because cargo-deny filters each dependency edge on its own: across all targets together it reports keyring's Linux-only zbus crates, which toolbox never builds. To run the suite on Linux locally, use a container with its own `CARGO_TARGET_DIR` (see `docs/development.md`), never the host `target/`.

Releases: pushing a `v*` tag runs `.github/workflows/release.yml`. A `version` job requires the tag to equal `v` + the `Cargo.toml` version. Then, in parallel: the `macos` job runs the tests and builds one universal macOS binary signed with the hardened runtime (`codesign --sign - --options runtime`) into `toolbox-macos.tar.gz`; the `linux` job runs on native `ubuntu-24.04` and `ubuntu-24.04-arm` runners, runs the tests against the musl target and builds static `toolbox-linux-x86_64.tar.gz` and `toolbox-linux-arm64.tar.gz` (musl, so no glibc version to match; it fails if the binary has an ELF interpreter). The `publish` job then creates the GitHub release with all three plus `SHA256SUMS` and the annotated tag's message as its notes (`--notes-from-tag`, so tag with `git tag -a vX -F notes.md` and no `#` lines), and renders `.github/homebrew/toolbox.rb` (placeholders `@VERSION@`, `@SHA256_MACOS@`, `@SHA256_LINUX_ARM64@`, `@SHA256_LINUX_X86_64@`) into `Formula/toolbox.rb` of `WilliamThogersen/homebrew-tap`. The formula picks the asset with `on_macos`/`on_linux` and `on_arm`/`on_intel`; `brew audit --strict` refuses `url` directly inside `on_macos`, which is why the macOS url sits in both arch blocks. The push to the tap uses the deploy key in the `HOMEBREW_TAP_DEPLOY_KEY` secret. Users install with `brew install WilliamThogersen/tap/toolbox`. `.github/workflows/brew-check.yml` runs after each release, weekly and on demand: it installs from the tap on a clean macOS runner and clean Linux runners (x86_64 and arm64) and fails unless that is the latest release, passing `brew test` and `brew audit --strict`, signed with the hardened runtime (macOS), static and with the vault off (Linux).
